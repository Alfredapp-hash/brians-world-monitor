The Webcam layer provides global visual intelligence by overlaying webcam locations on the map, with interactive tooltips showing preview images and a pinned webcam panel for persistent monitoring of key locations.

The layer draws on two kinds of source, merged into one set of markers:

1. **Openly published agency cameras** — transport authorities that publish their own camera directories as open data. No API key, no account, no proxying around an access control.
2. **Windy Webcams API v3** — a much larger global set, but one that requires a `WINDY_API_KEY`.

Only the first is available on a deployment with no credentials configured. Both use the same RPCs, the same clustering, and the same tooltip.

## Data Source: public agency cameras (no API key)

These are traffic authorities that publish a camera directory over anonymous HTTPS, along with the still images — and in some cases the video streams — that they already serve to the public web.

| Source | Operator | Cameras | Media | Attribution |
|---|---|---|---|---|
| Caltrans CCTV (districts 1–12) | California Dept. of Transportation | ~4,000 | JPEG still + HLS (`.m3u8`) | `Caltrans District N — California DOT open data` |
| TfL JamCams | Transport for London | ~890 | JPEG still + MP4 | `Powered by TfL Open Data` |
| NYC DOT traffic cameras | NYC Dept. of Transportation | ~970 | JPEG still | `NYC DOT Traffic Management Center` |

### What makes a source eligible

A camera is only included when all of the following hold. This is a deliberate line, not a technical limit:

- The operator publishes the directory itself as open data, over anonymous HTTPS.
- The image or stream URL is one the operator already serves to the public.
- No credential, session, or token is involved at any point.
- The operator is not signalling that the camera is down (`inService`, `available`, `isOnline` are all honoured).

Unsecured-camera aggregators are explicitly out of scope — see [Insecam in the limitations table](#no-live-video-api-exists-at-free-tier). Reachability is not permission.

### Sharding and cost

Source directories are large (a single Caltrans district is ~2MB of JSON), so they are split into bounded shards with a bounding box each: one per Caltrans district, one per city elsewhere. A viewport loads only the shards it overlaps, each cached for 6 hours, and a single request may pull at most 6 *uncached* shards — a whole-Earth view warms up over successive requests instead of downloading every directory at once. Already-warm shards are always served, however many overlap.

### Camera identifiers

Public cameras carry a `pub-<shard>-<localId>` identifier (for example `pub-nycdot-8a6bc417_4877_4ebe_8052_88c1b261baf1`). Operator ids are sanitized into the RPC's `[\w-]` charset, and the shard segment tells `getWebcamImage` which single directory to load for a lookup. The prefix is also what the client uses to pick the right credit line and "open at source" link instead of defaulting everything to Windy.

### Seeding and health

`scripts/seed-public-cameras.mjs` writes a **coverage manifest** — which sources answered, how many usable cameras each had, and their attributions — to `webcam:public-cameras:v1`, plus `seed-meta:webcam:public-cameras:v1` for `/api/health`. It deliberately does **not** seed camera positions; markers are live viewport reads, so a stale manifest means a source went dark rather than a blank layer. If every source fails, the previous payload is left in place rather than overwritten with zeroes.

## Data Source: Windy Webcams API v3

The primary data source is the [Windy Webcams API](https://api.windy.com/webcams/api/v3/docs), which provides approximately 65,000 camera locations worldwide.

| Attribute | Value |
|-----------|-------|
| **Provider** | Windy Webcams API v3 |
| **Coverage** | ~65,000 cameras globally |
| **Update frequency** | Cameras capture images periodically (every 5-15 min) |
| **Seeder** | `scripts/seed-webcams.mjs` — regional bounding-box fetch with adaptive quadrant splitting |
| **API key** | Required (`WINDY_API_KEY`); free tier available at [api.windy.com](https://api.windy.com) |
| **Attribution** | Required on free tier |

### What the API provides

**Seed-time fields** (bulk fetch with `include=location,categories`):

| Field | Description |
|-------|-------------|
| `webcamId` | Unique camera identifier |
| `title` | Camera name/description |
| `location.latitude` / `location.longitude` | Geographic coordinates |
| `location.country` | Country name |
| `location.region` | Region/state |
| `categories` | Camera category (traffic, landscape, city, etc.) |
| `status` | Camera status (active/inactive) |

**On-demand fields** (per-camera fetch with `include=images,urls`):

| Field | Description |
|-------|-------------|
| `images.current.preview` | Latest captured still image URL |
| `images.current.thumbnail` | Smaller thumbnail URL |
| `urls.player` | Embeddable timelapse player URL |
| `lastUpdatedOn` | Timestamp of last image capture |

### Free tier limitations

- Image token URLs expire after 10 minutes
- Bounding-box queries capped at 10,000 results per request (seeder uses adaptive quadrant splitting to work around this)
- Rate limits apply (seeder uses sequential regional fetches)

### API key configuration

The webcam layer requires a `WINDY_API_KEY` environment variable. Get a free key at [api.windy.com](https://api.windy.com).

| Environment | Where to set | Used by |
|-------------|-------------|---------|
| **Vercel** (production) | Project Settings > Environment Variables | `get-webcam-image.ts` (on-demand image/player URL fetches) |
| **Railway** (cron seeder) | Service Variables | `seed-webcams.mjs` (bulk metadata fetch) |
| **Tauri sidecar** (desktop) | Keychain via Settings > API Keys | On-demand image fetches via sidecar |
| **Local dev** | `.env` file | Both seeder and dev server |

Without the key:
- **Seeder** exits gracefully with "WINDY_API_KEY not set, skipping webcam seed"
- **Image handler** returns `{ error: 'unavailable' }` for Windy ids, and tooltips show "Preview unavailable"
- **Map layer** still renders the public agency cameras above, plus Windy markers from cached geo data if previously seeded

A missing Windy index is no longer fatal to the layer: `listWebcams` treats the seeded Windy set as one contributor and returns the public cameras on their own when it is absent.

## Architecture

```
Seed (periodic):
  Windy API        → seed-webcams.mjs        → Redis (geo index + metadata hash)
  Agency directories → seed-public-cameras.mjs → Redis (coverage manifest only)

Runtime:
  Browser map viewport → listWebcams RPC ─┬─ Redis geo search (Windy half, if seeded)
                                          └─ agency shard fetch (cached 6h)
                                          → merged, deduped, clustered response
  User clicks marker → getWebcamImage RPC ─┬─ pub-* id  → operator still/stream URL (no key)
                                           └─ Windy id  → Windy API (cached 5 min)
                                           → tooltip with preview
  User pins webcam → localStorage → PinnedWebcamsPanel (2x2 iframe grid)
```

### Backed by endpoints

The webcam layer does not hydrate marker or preview data from the bootstrap payload. Viewport reads are direct WebcamService RPC calls, and preview/player URLs are fetched only after a user interacts with a marker. Bootstrap carries one webcam key — `publicCameras` (`webcam:public-cameras:v1`, slow tier) — and it is the coverage manifest described above, not camera positions.

| Method | Route | What it feeds |
|--------|-------|---------------|
| `GET` | `/api/webcam/v1/list-webcams` | Map webcam markers and clusters for the current viewport; the handler reads seeded Redis geo/metadata keys and caches clustered viewport responses. |
| `GET` | `/api/webcam/v1/get-webcam-image` | Tooltip preview images and Windy player URLs for a selected camera; the handler calls Windy on demand and caches each webcam image lookup for 5 minutes. |

### Server-side clustering

The `listWebcams` handler performs server-side spatial clustering based on zoom level. At low zoom, nearby cameras are grouped into cluster markers showing a count. At higher zoom, individual markers appear. This keeps the map performant even when thousands of cameras are in view.

### Caching

Three cache layers work together to minimize latency and external API calls:

| Layer | Scope | TTL | Key |
|-------|-------|-----|-----|
| **Redis — geo + metadata** | Seeded camera index | 24 hours | `webcam:cameras:geo:{version}`, `webcam:cameras:meta:{version}` |
| **Redis — viewport responses** | Clustered results per map view | 24 hours | `webcam:resp:{version}:{zoom}:{quantizedBbox}` |
| **Redis — image lookups** | Per-webcam image/player URLs | 5 minutes | `webcam:image:{webcamId}` |
| **Client — image cache** | In-memory Map in browser | 9 minutes | webcamId |
| **Client — pinned store** | localStorage (permanent) | None (user-managed) | `wm-pinned-webcams` |

### Expected latency behavior

On first interaction after a container start, there is a noticeable delay as caches are cold:

1. **Map viewport change** → `listWebcams` RPC → server performs Redis geo search, builds clustered response, caches it. Subsequent identical viewports return instantly from Redis cache (24h TTL).
2. **First click on a webcam marker** → `getWebcamImage` RPC → server calls Windy API (network round-trip to external service), caches the response for 5 minutes server-side. The client also caches for 9 minutes — so re-clicking the same webcam within 9 minutes is instant with no server call.
3. **Pinning a webcam** → the player iframe loads from Windy's CDN (another external round-trip for the embed page). This is not cached by us — the browser handles iframe caching.

Once caches are warm, the only external calls are for webcams not viewed in the last 5-9 minutes.

### Redis data is ephemeral

Redis data does not survive container rebuilds. After rebuilding the stack, the seeder (`scripts/seed-webcams.mjs`) must re-run to repopulate the geo index and metadata. Without seeded data, the webcam layer will show no markers. Viewport response caches and image caches will rebuild organically as users interact with the map.

### No automatic re-seeding (known gap)

**This is a known limitation that needs to be addressed in a follow-up PR.**

The seeder writes geo and metadata keys to Redis with a 24-hour TTL, but nothing triggers a re-seed when those keys expire. After 24 hours without a manual re-seed, the webcam layer silently goes blank.

Current ways to re-seed:
- Run `scripts/seed-webcams.mjs` from the host
- Run `scripts/run-seeders.sh` (runs all seeders including webcams)
- **Railway cron** (recommended): schedule `seed-webcams.mjs` as a Railway cron service every 12-18 hours to stay ahead of the 24-hour TTL expiry

## Pinned Webcams Panel

Users can pin webcams from map tooltips to a persistent side panel. The panel displays up to 4 webcams simultaneously in a 2x2 grid of embedded Windy player iframes.

### Features

- **2x2 iframe grid**: Four active webcam players visible at once
- **Toggle on/off**: Webcams can be toggled between active (showing in grid) and inactive (in list only)
- **Overflow list**: When more than 4 webcams are pinned, a scrollable list appears below the grid for managing all pins
- **Pin from any renderer**: Pin buttons appear in webcam tooltips across all three map renderers (SVG, Globe, DeckGL)
- **Persistence**: Pinned webcams survive page reloads via localStorage
- **Custom events**: Panel updates reactively when pins change from any source

### Storage

Pinned webcam data is stored in `localStorage` under the key `wm-pinned-webcams`. Each entry contains:

```
webcamId, title, lat, lng, category, country, playerUrl, active (boolean), pinnedAt (timestamp)
```

Maximum 4 webcams can be active (showing in grid) at any time. The total number of pinned webcams is not limited.

## Current Limitations

### The Windy half is not live video

**This is the most important limitation to understand about the Windy cameras.** The Windy player does not show live video streams. Most webcams in the Windy network capture still images at periodic intervals (every 5-15 minutes). The embedded player compiles these stills into a timelapse, typically showing the last 24-72 hours of captures.

This means:
- The "player" is a timelapse of recent snapshots, not a live feed
- There is no way to filter for live-streaming cameras via the Windy API
- Real-time situational awareness is limited to the latest captured image (visible in the tooltip preview)

The public agency cameras refresh far faster — Caltrans stills update roughly every 5 minutes, and most Caltrans cameras additionally publish a genuine HLS stream — but they cover three metro regions, not the world.

### No live video API exists at free tier

No *global* free source of live video webcam feeds with a structured API exists. Live video requires streaming infrastructure (RTSP/HLS/WebRTC) which is expensive to operate. Individual public agencies do publish HLS for their own territory (Caltrans is wired up above); beyond that, known live sources are either paid, partner-only, or have no API:

| Source | Status |
|--------|--------|
| YouTube Live | Already integrated (Live YouTube panel) but not location-indexed |
| EarthCam | Partner-only, no public API |
| SkylineWebcams | No API |
| TrafficLand | 25K cameras with HLS but requires business coordination |
| Insecam | Legal liability (unsecured cameras), not viable |

### Other limitations

- **Free tier attribution**: Windy requires attribution when using free API tier
- **Image token expiry**: Preview image URLs from Windy expire after ~10 minutes; re-fetching is needed for stale tooltips
- **Seed coverage**: The seeder caps at 10K cameras per regional bounding box; adaptive quadrant splitting mitigates this but very dense regions may still miss cameras
- **No status filtering**: Inactive/offline cameras may appear on the map with broken previews
- **iframe sandbox**: Player iframes use `allow-scripts allow-same-origin allow-popups` sandbox policy

## Future Phases

### Phase 2: US DOT 511 State APIs — partially shipped

The keyless subset of this phase is live: Caltrans, TfL, and NYC DOT are wired up above, each with its own normalizing adapter in `server/worldmonitor/webcam/v1/public-cameras.ts`.

Remaining: the states whose 511 APIs require a per-state developer key (GA, AZ, UT, and 511ny's authenticated endpoints). Those need the key stored through the existing env pattern before their adapters are worth writing — no key is ever to be committed, and a state that cannot be reached anonymously stays out until one is configured.

Adding a source is a new entry in `PUBLIC_CAMERA_SHARDS` plus a parser: bounding box, URL, and a function returning `PublicCameraRecord[]`.

### Phase 3: OpenWebcamDB

Supplementary source with ~2,052 curated cameras. Free tier limited to 50 requests/day. Clean REST API but small dataset. Requires aggressive caching strategy.
